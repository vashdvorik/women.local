============================================================
  DEPLOY: Women Hub (womenhub.innovation.md)
============================================================

Хостинг: cPanel. PHP 8.3 = /usr/local/bin/ea-php83. Проект: ~/public_html/womenhub.innovation.md
Команды на сервере выполняются из папки проекта:

  cd ~/public_html/womenhub.innovation.md


------------------------------------------------------------
1. ПЕРЕД ПУШЕМ (на своём компьютере)
------------------------------------------------------------

  npm run verify        # сборка + тесты + проверка страниц, всё должно быть зелёным
  git add -A
  git commit -m "..."
  git push

  - Менялись стили или скрипты админки: сначала npm run build, public/build коммитится
    (Node на сервере нет).
  - .env и public/uploads в git не попадают, так и должно быть.


------------------------------------------------------------
2. ПЕРВАЯ УСТАНОВКА
------------------------------------------------------------

  Заранее, в cPanel:
  - база MySQL и пользователь;
  - PHP 8.3 с расширениями pdo_mysql, mbstring, openssl, tokenizer, xml, ctype, json, bcmath,
    fileinfo, curl, gd;
  - корень домена = папка public/ внутри проекта;
  - upload_max_filesize и post_max_size не меньше 25M (PDF в публикациях).

  git clone <репозиторий> .
  cp .env.example .env
  nano .env             # заполнить по разделу 5

  /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
  /usr/local/bin/ea-php83 artisan key:generate --force
  /usr/local/bin/ea-php83 artisan migrate --force
  /usr/local/bin/ea-php83 artisan db:seed --force
  /usr/local/bin/ea-php83 artisan storage:link
  /usr/local/bin/ea-php83 artisan optimize:clear
  /usr/local/bin/ea-php83 artisan nutgram:hook:set https://womenhub.innovation.md/telegram/webhook
  /usr/local/bin/ea-php83 artisan bot:sync-commands      # меню команд бота (ru, en, ro)

  Cron (cPanel, каждую минуту): очередь, в ней эмбеддинги и рассылки.

  * * * * * /usr/local/bin/ea-php83 /home/tirastyl/public_html/womenhub.innovation.md/artisan queue:work database --stop-when-empty --tries=3 >> /dev/null 2>&1

  Cron (cPanel, каждую минуту): расписание. Сверка платежей с банком (раз в 5 минут) и напоминания
  об окончании подписки в Telegram (раз в сутки). Без этой строки тариф после потерянного
  оповещения банка не включится сам, а напоминаний не будет.

  * * * * * /usr/local/bin/ea-php83 /home/tirastyl/public_html/womenhub.innovation.md/artisan schedule:run >> /dev/null 2>&1

4. ПЕРЕЗАПИСЬ БД С НУЛЯ
------------------------------------------------------------

  СТИРАЕТ ВСЁ: участниц из Telegram-бота, подписчиков, посты, ключи ИИ из админки.

  ПОСЛЕ НАЧАЛА БОЕВОГО ПРИЁМА ОПЛАТЫ ЭТО ДЕЛАТЬ НЕЛЬЗЯ: вместе с таблицами стираются платежи и подписки
  оплативших участниц (их деньги уже у банка), и тарифы придётся выдавать заново вручную. Номера новых
  счетов с прежними не совпадут (они не зависят от базы), но историю платежей это не возвращает.

  mysqldump -u ПОЛЬЗОВАТЕЛЬ -p БАЗА > backup.sql      # сначала дамп
  git pull
  /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
  /usr/local/bin/ea-php83 artisan migrate:fresh --seed --force
  /usr/local/bin/ea-php83 artisan optimize:clear

  Появится: админ из .env, 11 экспертов и 9 новостей с фото, темы сайта и кабинета.
  Не появится (так задумано): тестовые участницы, демо-тексты новостей, dev-вход, настройки и ключи ИИ.

  Не подошёл ADMIN_PASSWORD: контент всё равно загрузится, а команда закончится ошибкой.
  Исправьте .env и выполните:

  /usr/local/bin/ea-php83 artisan db:seed --class=AdminUserSeeder --force

7. НЕ ЗАБЫТЬ
------------------------------------------------------------

  - key:generate только при первой установке: повторный сбросит сессии и сделает нечитаемыми
    ключи ИИ, внесённые в админке.
  - vendor/ лежит в git вместе с dev-пакетами: после каждого git pull запускайте
    composer install --no-dev.
  - public/uploads не в git: доступен серверу на запись и входит в резервные копии
    (фото и PDF, загруженные в админке, восстановить нельзя).
  - Ключи API в сидерах и git не хранятся: вносите в админке («Кабинеты участниц → Настройки»).
  - Тексты бота лежат в resources/data/bot_messages.php, правки администратора — в базе
    («Кабинеты участниц → Сообщения бота»): git pull их не затирает, а перезапись БД с нуля (п. 4)
    вернёт исходные тексты из файла. Английский и румынский тексты — черновой перевод: вычитать.
    Если правили описания команд не из админки: artisan bot:sync-commands.
  - Подписки: после выкладки все одобренные участницы переходят на Open и теряют каталог, поиск и
    ИИ до оплаты или ручной выдачи тарифа («Кабинеты участниц → Подписки»). Если сообщество уже
    работает, заранее выдайте тариф тем, кому он положен.
  - artisan ai:recompute-embeddings — когда появятся участницы и внесены ключи ИИ.
  - Страницы новостей: текст и фото вносятся в админке (Новости → Изменить → «Текст страницы новости»).
    Демо-текст на боевом сервере не создаётся. Пока текста нет, «Подробнее» на карточке ведёт по внешней ссылке.

------------------------------------------------------------
8. СЕРВЕР ВЫШЕЛ ИЗ СТРОЯ: ВОССТАНОВЛЕНИЕ НА НОВОМ
------------------------------------------------------------

  Что хранится ВНЕ git и пропадёт вместе с сервером. Всё это должно лежать в резервной копии,
  причём ВНЕ самого сервера (другой хостинг, облако, ваш компьютер):

  1. База MySQL. Участницы, платежи, подписки, тексты бота, настройки, ключи ИИ. Дамп каждый день:
       mysqldump -u ПОЛЬЗОВАТЕЛЬ -p БАЗА > backup-ГГГГ-ММ-ДД.sql
  2. Файл .env (в git его нет). Особенно APP_KEY: им зашифрованы ключи ИИ в базе, без него их не прочесть.
     Ещё там пароль базы, токен бота, логин и пароль торговца банка, почта и пароль админа.
     Хранить в менеджере паролей, не в письме.
  3. Папка public/uploads (фото и PDF из админки, восстановить нельзя).
  4. Папка storage/app/public (аватары участниц из Telegram: storage/app/public/avatars).
  5. Строки cron из cPanel (раздел 2) и записи о домене/почте.

  Порядок восстановления на новом сервере (папка проекта, PHP 8.3):
    git clone <репозиторий> .
    cp ваш-сохранённый.env .env                     # тот же APP_KEY, НЕ выполнять key:generate
    /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
    mysql -u ПОЛЬЗОВАТЕЛЬ -p БАЗА < backup.sql        # база
    # вернуть public/uploads и storage/app/public из копии
    /usr/local/bin/ea-php83 artisan migrate --force   # на случай, если копия старее кода
    /usr/local/bin/ea-php83 artisan storage:link
    /usr/local/bin/ea-php83 artisan optimize:clear
    /usr/local/bin/ea-php83 artisan nutgram:hook:set https://womenhub.innovation.md/telegram/webhook
    /usr/local/bin/ea-php83 artisan bot:sync-commands
    # заново добавить две cron-строки из раздела 2 (очередь и schedule:run)
    # домен направить на новый сервер (DNS), включить HTTPS

  Проверка после восстановления:
    - вход в админку; /dev/account-login отвечает 404; участницы и подписки на месте;
    - artisan nutgram:hook:info показывает вебхук; боту можно написать;
    - artisan payments:reconcile спрашивает банк по счетам, которые ещё не закрыты.

  Что потеряется неизбежно: всё, что произошло между последним дампом и аварией.
    - Регистрации участниц в боте и правки в админке за это время.
    - ПЛАТЕЖИ. Деньги пришли в банк, а записи о счёте в восстановленной базе нет. Банк ResultURL
      повторно не вызывает (документ: после неудачного вызова считает его выполненным), а мы такой счёт
      не знаем. Что делать: открыть кабинет/выписку банка за период с последнего дампа, найти оплаченные
      счета (в описании есть Telegram ID плательщицы: «… tg12345678») и выдать тариф в админке
      («Подписки» → участница → «Выдать тариф»). Вернуть деньги можно только через банк.
    - Поэтому дамп базы нужен чаще раза в сутки, когда идёт приём платежей (хотя бы каждые 1–3 часа),
      и не рядом на том же диске.
  Мелочь после восстановления из старой копии: очередь заданий и счётчик напоминаний откатятся,
  и часть уведомлений в Telegram может прийти повторно.

  У банка заранее выяснить: ограничивает ли он доступ по IP сервера (запросы GetState идут с нашего
  адреса) и по какому адресу вызывает ResultURL. Если адрес сервера меняется, банк надо уведомить.
