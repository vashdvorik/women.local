============================================================
  DEPLOY: Women Hub (womenhub.innovation.md)
============================================================

Хостинг: cPanel. PHP 8.3 = /usr/local/bin/ea-php83. Проект: ~/public_html/womenhub.innovation.md
Команды на сервере выполняются из папки проекта:

  cd ~/public_html/womenhub.innovation.md

1. ПЕРЕД ПУШЕМ (на своём компьютере)
------------------------------------------------------------

  npm run verify        # сборка + тесты + проверка страниц, всё должно быть зелёным
  git add -A
  git commit -m "..."
  git push

  - Менялись стили или скрипты админки: сначала npm run build, public/build коммитится
    (Node на сервере нет).
  - .env и public/uploads в git не попадают, так и должно быть.

3. ОБНОВЛЕНИЕ
------------------------------------------------------------

  git pull
  /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
  /usr/local/bin/ea-php83 artisan migrate --force
  /usr/local/bin/ea-php83 artisan optimize:clear

  Старая версия стилей, скриптов и картинок у посетителей не остаётся, ничего делать не нужно:
    - стили, скрипты и картинки сайта подключаются с меткой ?v=время изменения файла (asset_v() в шаблонах,
      app/Support/Assets.php): файл поправили и выложили, адрес стал другим, браузер берёт новый;
    - файлы из /themes и /images Apache отдаёт с проверкой при каждом заходе (public/.htaccess, REVALIDATE_FILE): это
      подхватывает и то, что стили подтягивают сами (картинки и шрифты в url(...)), 304 без тела, если не менялось;
    - админка (/build) версионируется хешем в имени (npm run build, public/build коммитится), фото из админки —
      уникальным именем; страницы сайта браузер не кеширует.
  В новых шаблонах для файлов из public/ используйте asset_v(), а не asset() (это проверяет тест).
  Метка берётся из времени изменения файла на сервере: git pull обновляет его только у изменившихся файлов.

  Папка vendor/ в git НЕ хранится (она в .gitignore): после каждого git pull composer install
  обязателен, иначе сайт отвечает ошибкой 500. composer.lock в git есть, поэтому на сервер встают
  ровно те версии пакетов, что проверены на вашем компьютере.

  ОДИН РАЗ, при переходе с git-версии vendor/ (первое обновление после того, как vendor убрали из git):
  git pull удалит vendor/ с сервера, а ЕСЛИ composer когда-либо менял там файлы, git откажется тянуть
  изменения. Поэтому порядок такой (сайт при этом недоступен пару минут):

  git checkout -- vendor                 # вернуть vendor/ к состоянию git, убрать локальные правки composer
  git pull                               # vendor/ исчезнет
  /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
  /usr/local/bin/ea-php83 artisan optimize:clear

  Если composer install не может скачать пакеты (нет доступа к packagist.org с хостинга),
  не делайте git pull: сначала выясните это у хостинга.

  Нужен недостающий начальный контент (эксперты, новости, темы):
  /usr/local/bin/ea-php83 artisan db:seed --force
  Безопасно: ничего не дублирует и не затирает.

  Добавить на сайт новости организации (23 новости из архива постов: текст на русском, румынском и
  английском и фото). После git pull (он приносит тексты и сжатые фото) одна команда:

  /usr/local/bin/ea-php83 artisan db:seed --class=NewsArchiveSeeder --force

  Идёт около минуты: каждое фото проходит то же сжатие, что и загрузка в админке (кадр по слоту, WebP).
  Что произойдёт:
    - 20 новых новостей встанут наверх списка «Новости» по дате (старые карточки сдвинутся ниже);
    - три карточки, что уже есть на сайте (бизнес-форум, нетворкинг «Мечта обретает крылья» и
      международная конференция), получат полный текст, фото и настоящую дату, адрес и обложка
      останутся прежними;
    - повторный запуск безопасен: ничего не дублирует, текст, исправленный в админке, не трогает, а новость,
      удалённую в админке, не возвращает. Картинки, пропавшие с диска (папка uploads не в git),

  были сжаты до 1400 px и качества 76, а кадр сайта — до 60), после git pull сделайте две вещи:
    1. «Настройки сайта» → «Качество WebP»: поставьте 80 (новое значение по умолчанию; если поле никогда не
       сохраняли, оно подхватится само, если сохраняли со старыми 60 — поменяйте вручную и сохраните);

  нужную новость можно, удалив запись site_settings «news_archive» и запустив команду снова (тогда

5. .env НА ПРОДЕ
------------------------------------------------------------

  APP_NAME="Women's hub"                   # название в заголовках вкладок админки и кабинета
  APP_ENV=production                 # ОБЯЗАТЕЛЬНО: при local включится dev-вход и тестовые участницы
  APP_DEBUG=false                    # ОБЯЗАТЕЛЬНО
  APP_URL=https://womenhub.innovation.md
  APP_LOCALE=ru
  APP_FALLBACK_LOCALE=ru
  LOG_STACK=daily
  LOG_LEVEL=warning

  DB_CONNECTION=mysql
  DB_HOST=127.0.0.1
  DB_PORT=3306
  DB_DATABASE=...
  DB_USERNAME=...
  DB_PASSWORD=...

  SESSION_DRIVER=file                # сессии и кеш в файлах (storage/framework): публичные страницы не ходят за
  CACHE_STORE=file                   # ними в базу. Было database: при смене на file все, кто сейчас вошёл в
                                     # кабинет или админку, один раз войдут заново; затем: artisan optimize:clear
  SESSION_DOMAIN=womenhub.innovation.md
  QUEUE_CONNECTION=database

  Кеш публичных страниц (новости, фото, публикации, возможности, видео, проекты, эксперты, превью на главной)
  работает сам и от этих настроек не зависит: он всегда в файлах storage/framework/cache/public. Списки и
  страницы берутся оттуда, а не из базы; любое сохранение в админке сбрасывает его, а запись живёт не дольше
  15 минут. Если страница показывает устаревшее, сбросить вручную:

  /usr/local/bin/ea-php83 artisan public-cache:clear     # он же входит в artisan optimize:clear

  Папка storage/framework (cache, sessions, views) должна быть доступна PHP на запись. Если файлы кеша или
  сессий создал другой пользователь (например, команды запускали под root) и сайт ругается на права:

  find storage/framework -type d -exec chmod 775 {} \;
  find storage/framework -type f -exec chmod 664 {} \;

  Фото в браузере: public/.htaccess отдаёт /uploads и /build с заголовком «год, без проверки» (имена файлов
  уникальны: перекадрированное фото получает новое имя), остальные картинки и шрифты темы на неделю.
  Нужны модули Apache mod_headers и mod_setenvif (на cPanel включены); без них блок пропускается молча.
  Проверка: curl -sI https://womenhub.innovation.md/uploads/2026/10/ИМЯ.webp | grep -i cache-control

  ADMIN_NAME=...
  ADMIN_EMAIL=...                    # в админку пускает только эта почта
  ADMIN_PASSWORD=...                 # свой, случайный, не короче 12 символов; без change_me, password,
                                     # demo, admin, qwerty, 123456, example: такой пароль отклоняется
  TELEGRAM_TOKEN=...                 # настоящий: с заглушкой из .env.example вебхук отвечает 500
  TELEGRAM_COMMUNITY_URL=https://t.me/...    # ссылка на Telegram-сообщество: кнопки «Открыть Telegram» и
                                     # «Сообщество». НЕ адрес сайта (адрес сайта в сообщениях бота берётся из APP_URL).
                                     # Без этой строки кнопки ведут в бота https://t.me/WomenComBot
  GEMINI_API_KEY=...

  Подписки и оплата (подробно: docs/SUBSCRIPTIONS.md):
  SUBSCRIPTION_COMMUNITY_PRICE=600   # рублей за год: стартовая цена. Дальше её меняют в админке
  SUBSCRIPTION_PRIVATE_PRICE=20000   # («Подписки → Цена подписки на год»), и значения из .env перестают действовать
  WEBPAYMENT_DRIVER=bank             # на проде только bank; имитатор банка здесь не работает
  WEBPAYMENT_MERCHANT_LOGIN=...      # выдаёт банк; без них оплата отвечает «временно недоступна»
  WEBPAYMENT_MERCHANT_PASS=...
  WEBPAYMENT_TEST=true               # пока true, платежи тестовые и деньги не списываются.
                                     # Поставить false ТОЛЬКО после успешной проверки с банком,
                                     # затем artisan optimize:clear

7. НЕ ЗАБЫТЬ
------------------------------------------------------------

  - key:generate только при первой установке: повторный сбросит сессии и сделает нечитаемыми
    ключи ИИ, внесённые в админке.
  - vendor/ в git нет: после каждого git pull запускайте composer install --no-dev (раздел 3).
    Разовый переход со старой схемы, где vendor/ лежал в git, описан там же.
  - public/uploads не в git: доступен серверу на запись и входит в резервные копии
    (фото и PDF, загруженные в админке, восстановить нельзя).
  - storage/app/private/originals (сжатые фото целиком, по ним в админке меняют кадр картинок) не в git:
    доступна серверу на запись и тоже входит в резервные копии. Без неё сайт работает как обычно, пропадает
    только кнопка «Изменить кадр»: картинку придётся заменить, загрузив файл заново.
  - Фото есть на диске, а на сайте не открываются (пустая карточка с подписью вместо картинки):
    это права. Каталог нового месяца (public/uploads/ГГГГ/ММ) и файлы в нём должны быть доступны
    веб-серверу. Код теперь создаёт их правильно (0755 и 0644), но каталоги и файлы, созданные ДО этой
    правки, а также восстановленные из копии или залитые по FTP, надо исправить один раз:

      find public/uploads -type d -exec chmod 755 {} \;
      find public/uploads -type f -exec chmod 644 {} \;

    Если после сидера или восстановления фото снова не видны, выполните эти две команды ещё раз.
  - То же с папкой сжатых фото целиком storage/app/private/originals (по ним меняют кадр). Код создаёт в ней
    каталоги ГГГГ/ММ с 0755 и файлы с 0644 сам (config/filesystems.php, диск originals), но если папку
    восстанавливали из копии, заливали по FTP или она создана другим пользователем, чем PHP сайта, а
    «Изменить кадр» отвечает «нет сохранённого фото целиком» или ошибкой, выполните один раз:

      find storage/app/private/originals -type d -exec chmod 755 {} \;
      find storage/app/private/originals -type f -exec chmod 644 {} \;

    Сидер, запущенный по SSH, и загрузка из админки пишут в эту папку под одним и тем же пользователем
    хостинга (так устроен cPanel): если у вас иначе, владелец папки должен быть тем пользователем, под
    которым работает PHP сайта.
  - Ключи API в сидерах и git не хранятся: вносите в админке («Кабинеты участниц → Настройки»).
  - Тексты бота лежат в resources/data/bot_messages.php, правки администратора — в базе
    («Кабинеты участниц → Сообщения бота»): git pull их не затирает, а перезапись БД с нуля (п. 4)
    вернёт исходные тексты из файла. Английский и румынский тексты — черновой перевод: вычитать.
    Если правили описания команд не из админки: artisan bot:sync-commands.
  - Подписки: после выкладки все одобренные участницы переходят на Open и теряют каталог, поиск и
    ИИ до оплаты или ручной выдачи тарифа («Кабинеты участниц → Подписки»). Если сообщество уже
    работает, заранее выдайте тариф тем, кому он положен.
  - Вход в кабинет из бота: под сообщением об одобрении и под памяткой есть кнопка «Открыть кабинет»
    (мини-приложение, вход в одно касание по подписи Telegram). Она работает только при https в APP_URL
    и больше нигде не настраивается. Синяя кнопка «Кабинет» слева от поля ввода задаётся не в коде,
    а в @BotFather: Bot Settings → Menu Button; адрес должен быть https://<домен>/app/account/login.
    Если там остался чужой или старый адрес, кнопка откроет не тот сайт.
  - artisan ai:recompute-embeddings — когда появятся участницы и внесены ключи ИИ.
  - artisan ai:check-assistant — какая модель на самом деле отвечает ИИ-помощнику: показывает настройки,
    есть ли модель в списке провайдера и какое имя модели провайдер назвал в ответе на пробный запрос
    (ключ не печатается). Запускать после смены провайдера или модели чата. Опции: --model=имя и --tokens=N
    проверяют другое имя и лимит, а --provider=openrouter --model=имя — другого провайдера, не меняя
    настроек; --ask="вопрос" задаёт ассистенту настоящий вопрос
    (время ответа, токены, текст). Если ответ пустой при finish_reason=length, поднимите «Максимум токенов».
  - Страницы новостей: текст и фото вносятся в админке (Новости → Изменить → «Текст страницы новости»).
    Демо-текст на боевом сервере не создаётся. Пока текста нет, «Подробнее» на карточке ведёт по внешней ссылке.

8. СЕРВЕР ВЫШЕЛ ИЗ СТРОЯ: ВОССТАНОВЛЕНИЕ НА НОВОМ
------------------------------------------------------------

  Что хранится ВНЕ git и пропадёт вместе с сервером. Всё это должно лежать в резервной копии,
  причём ВНЕ самого сервера (другой хостинг, облако, ваш компьютер):

  1. База MySQL. Участницы, платежи, подписки, тексты бота, настройки, ключи ИИ. Дамп каждый день:
       mysqldump -u ПОЛЬЗОВАТЕЛЬ -p БАЗА > backup-ГГГГ-ММ-ДД.sql
  2. Файл .env (в git его нет). Особенно APP_KEY: им зашифрованы ключи ИИ в базе, без него их не прочесть.
     Ещё там пароль базы, токен бота, логин и пароль торговца банка, почта и пароль админа.
     Хранить в менеджере паролей, не в письме.
  3. Папка public/uploads (фото и PDF из админки, восстановить нельзя).
  4. Папка storage/app/public (аватары участниц из Telegram: storage/app/public/avatars).
  5. Папка storage/app/private/originals (сжатые фото целиком для перекадрирования картинок; без неё
     сайт работает, но «Изменить кадр» перестаёт открываться).
  6. Строки cron из cPanel (раздел 2) и записи о домене/почте.

  Порядок восстановления на новом сервере (папка проекта, PHP 8.3):
    git clone <репозиторий> .
    cp ваш-сохранённый.env .env                     # тот же APP_KEY, НЕ выполнять key:generate
    /usr/local/bin/ea-php83 composer.phar install --no-dev --optimize-autoloader
    mysql -u ПОЛЬЗОВАТЕЛЬ -p БАЗА < backup.sql        # база
    # вернуть public/uploads, storage/app/public и storage/app/private/originals из копии, затем исправить права (раздел 7):
    find public/uploads -type d -exec chmod 755 {} \;
    find public/uploads -type f -exec chmod 644 {} \;
    /usr/local/bin/ea-php83 artisan migrate --force   # на случай, если копия старее кода
    /usr/local/bin/ea-php83 artisan storage:link
    /usr/local/bin/ea-php83 artisan optimize:clear
    /usr/local/bin/ea-php83 artisan nutgram:hook:set https://womenhub.innovation.md/telegram/webhook
    /usr/local/bin/ea-php83 artisan bot:sync-commands
    # заново добавить две cron-строки из раздела 2 (очередь и schedule:run)
    # домен направить на новый сервер (DNS), включить HTTPS

  Проверка после восстановления:
    - вход в админку; /dev/account-login отвечает 404; участницы и подписки на месте;
    - artisan nutgram:hook:info показывает вебхук; боту можно написать;
    - artisan payments:reconcile спрашивает банк по счетам, которые ещё не закрыты.

  Что потеряется неизбежно: всё, что произошло между последним дампом и аварией.
    - Регистрации участниц в боте и правки в админке за это время.
    - ПЛАТЕЖИ. Деньги пришли в банк, а записи о счёте в восстановленной базе нет. Банк ResultURL
      повторно не вызывает (документ: после неудачного вызова считает его выполненным), а мы такой счёт
      не знаем. Что делать: открыть кабинет/выписку банка за период с последнего дампа, найти оплаченные
      счета (в описании есть Telegram ID плательщицы: «… tg12345678») и выдать тариф в админке
      («Подписки» → участница → «Выдать тариф»). Вернуть деньги можно только через банк.
    - Поэтому дамп базы нужен чаще раза в сутки, когда идёт приём платежей (хотя бы каждые 1–3 часа),
      и не рядом на том же диске.
  Мелочь после восстановления из старой копии: очередь заданий и счётчик напоминаний откатятся,
  и часть уведомлений в Telegram может прийти повторно.

  У банка заранее выяснить: ограничивает ли он доступ по IP сервера (запросы GetState идут с нашего
  адреса) и по какому адресу вызывает ResultURL. Если адрес сервера меняется, банк надо уведомить.
